# Failure analysis

## The agent faithfulness gate on holdout

### Symptom

The first full holdout run failed the release gate on one metric: `agent.faithfulness` was 0.75 (6 of 8 policy questions) against a gate of 0.90 (`evals/reports/2026-10-21-holdout-2.json`; the recording run is `2026-10-21-holdout.json`). Every other stage passed. On dev the same agent and judge scored 1.00 on 18 policy questions (`2026-10-21-dev-12.json`), so either the dev set was too easy or something failed only on questions I had not looked at.

I read the holdout cassettes and the report once to find out why, and did not change a prompt or a threshold on what I saw there. Each change below is backed by a dev reproduction or by a unit test with made-up clause text. After the changes I re-recorded the holdout agent and judge cassettes once and ran the gate once.

### What the cassettes showed

Two policy questions failed and one passed when it should not have. Two claim-data questions (not gated) also failed.

**AQ-027, a correct answer rejected by code.** The agent answered "The policyholder pays a $50 excess on this glass claim", citing 4.2 and 5.1. The judge cassette (`judge__AQ-027`) has one statement, `supported: true`, with the quote "You pay the following excess on each claim: glass claims $50;". The judge model got this right; the code in `src/claimcheck/agent/judge.py` turned it down. The clause reads "...on each claim: collision claims $300; glass claims $50; ...", so the quote leaves out the collision entry. `_quoted` accepted a quote only if it was a substring of the clause text or scored at least 90 on `fuzz.partial_ratio`. This one scored 88.3. A correct quote that shortens a list fell just under the threshold.

**AQ-033, the agent stated a condition as a fact.** Asked "Is the theft covered if the keys were left in the vehicle?", the agent wrote "No. The theft is not covered because the keys were left in or on the vehicle". The judge split this into a supported policy statement and "The claim is not covered due to the keys being left in the vehicle", labelled `claim` with an empty quote. Every statement of a policy answer is checked, so the empty quote fails it. This rejection is right. The agent called only `search_policy_clauses`, so nothing told it how this theft happened, and the claim form says the opposite ("I still have both keys"). An adjuster skimming the answer would come away with a false fact about the claim.

**AQ-034, an answer that passed but should not have.** Asked which documents a glass claim needs, the agent searched "glass breakage" instead of the documents clause and described the glass cover. The judge accepted "A glass claim needs the invoice or estimate..." as supported by the cover sentence of 4.2. Only `citation_hit` caught it. So 0.75 already flattered the agent by one question.

**AQ-032 (claim data), the judge had no evidence for a true answer.** The agent called `get_policy_version`, which returned `version_no: null` and the note "no policy version was in force on the incident date, so no clause applies", and answered exactly that. The judge labelled both statements `policy` and quoted the prompt's own placeholder ("(no clauses: ... for example because no policy version was in force ...)"). The code checks quotes against the cited clause text, which was empty, so neither quote could pass. Dev question AQ-025 had failed in every dev run so far (`dev-7` to `dev-12`). The judge never saw the one tool result that backed the answer.

**AQ-029 (claim data), out of turns.** "Which document is missing?" The agent called six different tools in a row: summary, documents, fields, policy version, a "theft excess" search, then `get_validation_results`, whose R6 message ("Missing for a theft claim: incident_report") was the answer. The sixth turn's call is never run. It did not repeat a call, so this is not a loop. The summary names the blocking rule but not its message, and the model took the long way round.

### What I changed, and the evidence for each

**1. Shortened quotes (AQ-027).** A quote may now leave out entries of a list. It is split only at colons and semicolons, and it counts if every part is verbatim, at least three words long and found in order within one clause, and the words it skips contain no sentence end. A test I added afterwards showed why that last condition is needed: my first version also split at sentence ends, so a quote could step over a whole exclusion sentence ("We cover theft of the vehicle. ... if the keys were left in or on the vehicle" passed). While writing the tests I found the opposite hole in the fuzzy path: "You pay the following excess on each claim: collision claims $90" scores 98 against a clause that says $700 for collision and $90 for glass, so a quote with a changed amount passed. Another test showed that an exact match can cut a number short ("$70" inside "$700", "$9" inside "$90"). On every path, each amount in the quote must now be a whole amount in the clause text it matched. The tests are in [`tests/agent/test_judge.py`](../tests/agent/test_judge.py): for example, `test_a_quote_that_leaves_out_part_of_a_list_still_counts` fails on the original code, and `test_a_shortened_quote_cannot_skip_a_sentence` fails on my first version. The others make sure the rule cannot be used to stitch a quote together.

**2. The no-version note as evidence (AQ-025 on dev, AQ-032 on holdout).** The loop keeps the note from `search_policy_clauses` or `get_policy_version` when they report no version (`AgentAnswer.policy_notes`). The judge is shown it in place of clauses, and its quotes are checked against it as well as against clause text. A policy amount still cannot be quoted from the note, because the note has none. Tests: `test_a_policy_tools_no_version_note_is_kept_for_the_judge`, `test_a_note_about_a_version_in_force_is_not_kept`, `test_the_no_version_note_is_kept_once` (`tests/agent/test_loop.py`), `test_judge_is_shown_the_no_version_note`, `test_a_statement_that_repeats_the_no_version_note_is_supported`, `test_the_no_version_note_does_not_support_a_policy_term`. I needed three dev runs to get this right. First I told the judge in its system prompt that it could quote the note (`dev-16`). AQ-025 passed, but the changed instructions made the judge quote the wrong sentence for a correct $50 glass excess on AQ-004. Then I showed the note without any instruction (`dev-17`), and the judge left the quote empty. The final version puts the instruction next to the note, in the prompt of the answers that have one, so no other judge prompt changes (`dev-19`, drift 0).

**3. Tried and reverted: an agent rule for "is it covered if" questions (AQ-033).** I needed this failure on dev before touching the prompt, so I added seven conditional dev questions (AQ-037 to AQ-043). Six take their condition from clauses other than the theft clause (alcohol, rallies, Europe, a suspended licence, a lapsed premium, mechanical breakdown). The seventh, AQ-043, is deliberately close to the holdout question: the same question form ("Is the theft covered if ...?") on the same theft clause, 4.3, with a different condition from that clause (a police report three days late instead of keys left in the car). Five of the first six were answered without turning the condition into a fact, and one came back as an empty reply (`dev-14`). The late-report question reproduced the failure (`dev-15`): "the theft is not covered as it was reported more than 48 hours after discovery", plus a `flag_for_review` call that nobody asked for. I tried two wordings: a separate rule (`dev-20`), and one sentence in rule 1 plus an example answer (`dev-21`). Neither fixed AQ-043. Both scored 0.84 on dev, against 0.88 for the original prompt recorded again afterwards (`dev-22`, replayed under the final code as `dev-23`). The first gave a policy answer with no search at all (AQ-009) and four more flag calls nobody asked for. The second cited a clause that was never retrieved (AQ-002). I put the original prompt back.

**4. Not changed: the turn budget (AQ-029).** The budget stays at 6. No dev question has run out of turns, and the only repeated calls on dev are two identical searches in one turn, which cost a tool call but not a turn.

The holdout re-recording (`2026-10-21-holdout-3.json`, first gate run `holdout-4`) produced the same eleven answers as before, word for word. Only the judge's verdicts changed: AQ-027 and AQ-032 now pass, AQ-033 still fails. The later fixes to the quote check only made it stricter, so both splits were scored again by replaying the same cassettes with no new model output (`dev-23`, `holdout-5`, drift 0). No verdict changed on either. The gate command exits 1 with `agent.faithfulness` 0.875 against 0.90. The other gated metrics are unchanged (classification 1.00, extraction F1 0.933, recall@5 1.00, wrong-version hits 0, validation 1.00).

The final dev number is lower than `dev-19` because of AQ-020, and the change of prompt is not the cause. All three fresh recordings of the evening (`dev-20`, `dev-21` and `dev-22`, the last with the original prompt) word that answer as "The collision limit that applies is $25,000 per claim, less the collision excess of $500.", where the earlier recording said "The collision limit is ...". For this wording the judge quotes the cross-reference "less the collision excess in section 5.1" instead of the $500 in 5.1, so the amount check fails a correct answer. The shift is stable, not random, but it shows how far a recording can move without any change on my side: the earlier answer was recorded for the very same request (it replayed with drift 0 in `dev-15`), at temperature 0. On 8 holdout policy questions one question is 0.125, so at this size the 0.90 gate means 8 of 8.

### What remains

- **The CI gate is still red.** AQ-033 is a real fault, and a prompt rule did not fix it in two attempts on dev. Next I would try a model that follows the instruction (the same eval on the Anthropic or OpenAI backend is one setting plus one recording run), and write more dev questions of this kind before another prompt attempt.
- The judge is a 7B model too. It still accepts loose support (AQ-034) and sometimes quotes the wrong sentence (AQ-020). The code checks catch wrong quotes and amounts, but not a wrong claim of support. More holdout questions would also make one flip cost less than 0.125.
- AQ-029: putting the blocking rules' messages into `get_claim_summary` would answer "what is missing" in one call. No dev question shows the problem yet, so I have not changed it.
- Claim-data answers: AQ-017 still comes back as plain text instead of JSON, AQ-039 was an empty reply on the first turn, and the agent sometimes calls `flag_for_review` without being asked (harmless, since only a person can confirm a flag, but it costs a turn).

The holdout data was inspected once, for this diagnosis, and its agent and judge cassettes were re-recorded once after the changes. I am not going to tune against it again.

## Extraction: tightening the evidence rule

The extraction F1 on dev went 0.850, 0.922, 0.921 (`2026-10-21-dev.json`, `-dev-2`, `-dev-5`; ADR-003). Most of the first jump came from one finding: in box and table layouts, Tesseract reads columns in order, so the model's quote ("POLICY NO.\nAUT-104233") joined a label to a value that are not next to each other in the OCR text. Correct values were marked `source_not_found` and halved. Looking up the value itself when it appears in the quote recovered about 60 fields with no prompt change, measured on the same cassettes.

That fix let in too much, and three probe tests showed how: a value missing from a real quote (`test_value_absent_from_a_real_quote_is_not_found`), an identifier one character off (`test_one_character_off_identifier_is_not_found`), and a date quoted by its label alone (`test_date_quoted_by_its_label_alone_is_not_found`). Requiring the value to sit inside the located quote closed all three, at a cost of 0.001 F1. A looser variant scored 0.922 again (`dev-4`) but let a wrong claimant name through with high confidence, because the OCR had misread the same name on the signature line. I kept the stricter rule.
